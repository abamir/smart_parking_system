# Smart Parking Management System — API Documentation

## 1. Overview

The Smart Parking Management System exposes REST APIs for:

- Parking availability
- Vehicle check-in
- Vehicle check-out
- Parking fee and payment processing

### Base URL

```text
http://localhost:8080
```

### Parking API Base Path

```text
/api/v1/parking
```

### Content Type

For POST requests:

```http
Content-Type: application/json
```

---

# 2. API Summary

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/v1/parking/availability` | Get current parking availability |
| POST | `/api/v1/parking/check-in` | Check in a vehicle |
| POST | `/api/v1/parking/check-out` | Check out a vehicle and record payment |

---

# 3. Standard Success Response

Successful APIs use a wrapper similar to:

```json
{
  "success": true,
  "message": "Operation completed successfully",
  "data": {},
  "timestamp": "2026-07-24T16:02:09.1539767"
}
```

Fields:

| Field | Description |
|---|---|
| `success` | Indicates whether the operation succeeded |
| `message` | Human-readable result message |
| `data` | API-specific response payload |
| `timestamp` | Response timestamp |

---

# 4. Standard Error Response

Errors use a response similar to:

```json
{
  "error": "Bad Request",
  "message": "Vehicle number is required",
  "status": 400,
  "timestamp": "2026-07-24T20:02:55.6132127",
  "path": "/api/v1/parking/check-in"
}
```

Fields:

| Field | Description |
|---|---|
| `error` | HTTP error description |
| `message` | Application error message |
| `status` | HTTP status code |
| `timestamp` | Time the error occurred |
| `path` | Requested API path |

---

# 5. Get Parking Availability

Returns the number of currently available parking spots by type.

## Endpoint

```http
GET /api/v1/parking/availability
```

## Request Body

None.

## Example

```bash
curl http://localhost:8080/api/v1/parking/availability
```

## Successful Response

**HTTP 200 OK**

```json
{
  "success": true,
  "message": "Parking availability fetched successfully.",
  "data": {
    "bikeAvailable": 8,
    "compactAvailable": 8,
    "largeAvailable": 8,
    "busAvailable": 4
  },
  "timestamp": "2026-07-24T16:02:09.1539767"
}
```

The actual counts depend on current parking-lot state.

# 6. Vehicle Check-In

Checks a vehicle into the parking facility.

The operation:

```text
Validates Request
       ↓
Checks Existing Active Parking
       ↓
Finds/Creates Vehicle
       ↓
Allocates Compatible Spot
       ↓
Marks Spot OCCUPIED
       ↓
Creates ACTIVE Ticket
       ↓
Returns Ticket
```

## Endpoint

```http
POST /api/v1/parking/check-in
```

## Request

```json
{
  "vehicleNumber": "MH27BD3354",
  "ownerName": "Amir",
  "vehicleType": "CAR"
}
```

## Request Fields

| Field | Required | Description |
|---|---|---|
| `vehicleNumber` | Yes | Vehicle registration number |
| `ownerName` | Yes | Vehicle owner's name |
| `vehicleType` | Yes | Type of vehicle |

---

# 7. Check-In Validation

### `vehicleNumber`

Validation includes:

```java
@NotBlank
@Size(max = 20)
```

Therefore it must:

- Be provided
- Not be blank
- Not exceed 20 characters

### `ownerName`

Validation includes:

```java
@NotBlank
@Size(max = 100)
```

Therefore it must:

- Be provided
- Not be blank
- Not exceed 100 characters

### `vehicleType`

Validation:

```java
@NotNull
```

It must correspond to a supported `VehicleType` enum value.

Examples include:

```text
CAR
SUV
MOTORCYCLE
TRUCK
BUS
```

---

**HTTP 200 OK**

  "data": {

    "floorNumber": 1,
    "entryTime": "2026-07-24T18:51:24.2024925",
    "exitTime": null,
    "totalFee": null,
    "status": "ACTIVE"
  }

The exact spot and ticket number are generated by the application.

---

# 10. Duplicate Vehicle Check-In

A vehicle should not have another active parking session while already parked.

Example request:

```json
{
  "vehicleNumber": "MH27BD3354",
  "ownerName": "Amir",
  "vehicleType": "CAR"
}
```

If the vehicle already has an active ticket, the API returns:

```text
409 Conflict
```

This is handled through the application's business exception mechanism.

---

# 11. Parking Spot Unavailable

If no compatible parking spot is available, check-in cannot proceed.

The API returns:

```text
409 Conflict
```

The failed check-in transaction should not leave partially updated parking state.

---

# 12. Vehicle Check-Out

Completes an active parking session.

The operation:

```text
Validate Request
      ↓
Find ACTIVE Ticket
      ↓
Close Ticket
      ↓
Calculate Parking Fee
      ↓
Save Fee
      ↓
Record Payment
      ↓
Payment SUCCESS?
      ↓
Release Parking Spot
```

## Endpoint

```http
POST /api/v1/parking/check-out
```

---

# 13. Check-Out Request

```json
{
  "ticketNumber": "TKT-1784901995492-89B1E",
  "vehicleNumber": "MH27BD3354",
  "paymentMode": "UPI",
  "paymentStatus": "SUCCESS"
}
```

## Request Fields

| Field | Required | Description |
|---|---|---|
| `ticketNumber` | Yes | Ticket generated during check-in |
| `vehicleNumber` | Yes | Vehicle registration number |
| `paymentMode` | Yes | Payment method |
| `paymentStatus` | Yes | Payment result |

---

# 14. Check-Out Validation

The current DTO requires:

```java
@NotNull
private String ticketNumber;

@NotNull
private String vehicleNumber;

@NotNull
private PaymentMode paymentMode;

@NotNull
private PaymentStatus paymentStatus;
```

Therefore all four fields must be provided.

Supported enum values depend on the corresponding application enums.

A known example is:

```text
paymentMode   = UPI
paymentStatus = SUCCESS
```

---

# 15. Check-Out Example Using curl

```bash
curl -X POST http://localhost:8080/api/v1/parking/check-out ^
-H "Content-Type: application/json" ^
-d "{\"ticketNumber\":\"TKT-1784901995492-89B1E\",\"vehicleNumber\":\"MH27BD3354\",\"paymentMode\":\"UPI\",\"paymentStatus\":\"SUCCESS\"}"
```

---

# 16. Successful Check-Out

On successful checkout:

```text
ParkingTicket
ACTIVE → COMPLETED

exitTime
NULL → current exit time

totalFee
NULL → calculated amount

Payment
created

ParkingSpot
OCCUPIED → AVAILABLE
```

The API returns the payment response wrapped in the standard success response.

# 19. Invalid Enum Values

Fields such as:

```text
vehicleType
paymentMode
paymentStatus
```

are Java enums.

Values should match supported enum constants.

For example:

```json
{
  "paymentMode": "UPI"
}
```

rather than an unsupported value.

# 20. HTTP Status Codes

| Status | Meaning | Example |
|---|---|---|
| `200 OK` | Request completed successfully | Availability/check-in/check-out |
| `400 Bad Request` | Request validation or malformed input | Missing required field |
| `404 Not Found` | Requested resource/ticket not found | No active ticket |
| `409 Conflict` | Business-state conflict | Vehicle already parked |
| `500 Internal Server Error` | Unexpected server-side failure | Unhandled system error |

# 22. Recommended Manual Test Flow

Start with:

```text
GET /availability
```

Record the current number of available spots.

Then:

```text
POST /check-in
```

Verify:

```text
ticket status = ACTIVE
spot status   = OCCUPIED
```

Call availability again and verify the corresponding available count decreases.

Then:

```text
POST /check-out
```

with:

```text
paymentStatus = SUCCESS
```

Verify:

```text
ticket status = COMPLETED
payment       = created
spot status   = AVAILABLE
```

Call availability again and verify the spot count returns.

# 25. API Design Principles

The API follows several important practices:

- DTOs are used instead of exposing JPA entities.
- Request validation occurs before business processing.
- Business exceptions map to appropriate HTTP statuses.
- Responses use a consistent wrapper.
- Database operations are handled through the service layer.
- Check-in/check-out operations use transaction boundaries.
- Persistence relationships are not directly serialized to API clients.
- Swagger/OpenAPI documents the public API contract.
